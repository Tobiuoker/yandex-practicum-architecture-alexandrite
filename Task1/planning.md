# Планирование: анализ, идентификация проблем и поиск решений

## Проблемные места

* Рассинхрон статусов заказа или же их "не доезжание" до CRM. Из-за чего их просто не могут взять в работу. 
  
  Возможные решения:
  * Возможно данные просто даже не записываются в топик из-за негрантированной доставки. Необходимо записывать сообщения в топик через паттерн transactional outbox, чтобы гарантировать публикацию сообщения в очередь. Для этого можно выделить работу с outbox в отдельный переиспользуемый модуль, т.к. в топик пишут несколько сервисов и всем нужна эта гарантия
   
* Переполнение очереди из-за огромного количества заказов из разных источников
  
  Возможные решения:
  * необходимо добавить разные очереди для B2B и B2C заказов, чтобы они не мешали друг другу
  * Добавить backpressure в виде `prefetch_count` на стороне консьюмеров, чтобы их не перегружать огромным кол-вом сообщений 
* Долгая загрузка списка заказов

  Возможные решения:
  * Оптимизация запросов на получение списка. Необходимо переехать с `offset pagination` на курсорную, т.к. с ней не придется сканить всю БД и с ростом кол-ва записей она не ухудшается в производительности. Пагинация будет по составному курсору - `created_at` и `id`
  * Можно также добавить refresh ahead кеширование 
* Невозможность получить актуальный список новых заказов в реальном времени

  Возможные решения:
  * Добавление чтения ивента заказов, чтобы реагировать на добавление новых заказов и обновлять страницу, чтобы у всех были равные условия получения актуальной информации по заказам
* Затянутый релизный цикл

  Возможные решения:
  * Внедрить автоматизацию в тесты - должно быть бОльшее покрытие unit тестами, а также достаточное кол-во интеграционных тестов, чтобы значительно уменьшить ручные сценарии.
  * Раскатку потенциально опасных фичей нужно закрывать за фичефлагами
* Недоступность сервисов из-за возросшей нагрузки (единственный инстанс сервиса не справляется).

  Возможные решения:
  * Если рассмтаривать MES API, то очень длительный расчет цены не должен быть синхронным. Необходимо сохранять запрос на расчет в табличку и отправлять их в очередь отдельным воркеров, который будет потом оповещать пользователя об окончании расчетов. Можно также на основе кол-ва сообщений в очереди настроить backpressure в MES API, чтобы уменьшить кол-во запросов
  * В кэш добавлять кол-во запросов с каждого отдельного партнера и ограничивать их (также место для монетизации)
  * Переезд инфраструктуры на kubernetes. На данный момент по одному поду на каждый инстанс - это критически мало из-за чего получается невозможно поскейлить приложение в зависимости от нагрузки.
  * После добавления kubernetes можно также внедрить api gateway для балансировки поступающей нагрузки (а также для авторизации/аутентификации и возможного добавления кеширования с rate-limiting'ом)

* Связность двух сервисов с одной БД

  Возможные решения:
  * Нужно сделать отдельную БД на каждый сервис, т.к. запросы из двух сервисов в одну БД критически влияют на ее производительность и является основным боттлнеком системы

* Дублирование запросов на создание заказа или расчет стоимости

  Возможные решения:
  * Нужно добавить токен идемпотентности перед в запросы и сохранять их в кеше или табличке для дальнейшей проверки запросов

* Отсутствие наблюдаемости системы

  Возможные решения:
  * Необходимо добавить логирование иземенений внутри системы, трейсинг запросов от сервиса к сервису, а также в целом добавить дешбродов о состоянии системы. Потенциальные метрики, за которыми необходимо следить:
    * RPS в каждом отдельном сервисе
    * Кол-во ошибок
    * Latency запросов по каждому сервису
    * Read/write lag топиков
    * Кол-во сообщений в каждом топике
    * Кол-во заказов с разбивкой по каждому статусу
    * Время нахождения заказов в нетерминальных статусах

## Приоритет

1. Добавление наблюдаемости
2. Разделение БД сервисов
3. Сделать расчет стоимости заказа асинхронным


## Целевая архитектура через полгода

Через полгода система должна перейти от текущей архитектуры с синхронной обработкой тяжeлых операций и единичными экземплярами сервисов к более масштабируемой и отказоустойчивой модели.

Основные изменения:

- Расчeт стоимости изделия в MES выполняется асинхронно. Запрос быстро принимается системой и помещается в очередь, а расчeт выполняется отдельными воркерами. Это позволяет независимо масштабировать вычислительную нагрузку и не блокировать API
- Потоки B2B и B2C заказов разделены по отдельным очередям и обрабатываются независимо. Для B2B API действуют rate limiting и квоты, а consumers используют backpressure, чтобы рост входящего потока не приводил к перегрузке системы
- Обмен событиями между системами становится надeжным - используется transactional outbox, consumers обрабатывают сообщения идемпотентно.
- MES и другие наиболее нагруженные компоненты могут горизонтально масштабироваться. Перед экземплярами приложений используется балансировщик нагрузки. Для внешнего B2B API используется API Gateway с ограничением и контролем входящего трафика.
- У сервисов устраняется совместное владение базами данных. Каждый сервис становится владельцем своих данных, что уменьшает связанность компонентов и позволяет масштабировать их независимо.
- Для MES дешборда оптимизируется запрос за списком заказов -  используется курсорная пагинация и необходимые индексы (еще по `created_at`), а получение новых заказов происходит событийно, без постоянного полного перечитывания списка.
- В систему добавляется полноценная наблюдаемость - централизованные логи, трейсы, технические и бизнес метрики. Отслеживаются состояние очередей, latency, кол-во ошибок, нагрузка на сервисы, количество заказов в каждом статусе и время нахождения заказа в статусе.
- Критические unit, интеграционные сценарии автоматизируются и запускаются в CI/CD. Новая функциональность при необходимости выпускается под фичафлагами, благодаря чему дефект одной функции не блокирует выпуск остальных изменений.

В результате архитектура должна позволять независимо масштабировать наиболее нагруженные части системы, контролировать входящую нагрузку, не терять заказы и события, а также обнаруживать проблемы до того, как о них сообщат клиенты.
