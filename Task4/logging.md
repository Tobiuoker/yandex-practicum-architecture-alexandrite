# Архитектурное решение по логированию

## 1. Что логируем

В первую очередь централизованно собираем логи из:

- Shop API;
- CRM API;
- MES API;
- интеграции с RabbitMQ;
- PostgreSQL - ошибки, блокировки и медленные запросы;
- RabbitMQ - ошибки брокера, подключений и очередей.

Фронтенды и хранилище 3D-файлов на первом этапе отдельно не логируем. Результат работы с ними фиксируется на стороне API.

### Логи уровня INFO

| Система | Событие | Что записываем |
|---|---|---|
| Shop API | Создание заказа | время, `order_id`, внутренний `customer_id`, источник, статус |
| Shop API | Загрузка 3D-модели | `order_id`, `file_id`, размер файла, результат |
| Shop API | Отправка заказа | `order_id`, старый и новый статус |
| CRM API | Получение заказа/события | `order_id`, `message_id`, источник |
| CRM API | Изменение статуса | `order_id`, старый и новый статус |
| MES API | Прием заказа через API | `order_id`, `partner_id`, результат |
| MES API | Запуск и завершение расчета стоимости | `order_id`, длительность, результат |
| MES API | Изменение производственного статуса | `order_id`, старый и новый статус |
| Интеграция RabbitMQ | Успешная публикация сообщения | `order_id`, `message_id`, очередь, тип события |
| Интеграция RabbitMQ | Успешная обработка сообщения | `order_id`, `message_id`, очередь, результат |
| Outbox после его внедрения | Создание и успешная публикация события | `order_id`, `event_id`, тип события |

Во все прикладные логи также добавляем:

- имя сервиса;
- окружение;
- `trace_id` и `span_id`;
- идентификатор запроса;
- результат операции;
- длительность операции, если она значима.


### Другие уровни логирования

**WARN**:
- медленная операция;
- временная недоступность БД или RabbitMQ;
- отклоненный переход заказа в некорректный статус.

**ERROR**:
- необработанное исключение;
- ошибка записи бизнес-данных в БД;
- невозможность опубликовать сообщение после повторных попыток;
- ошибка расчета стоимости;
- ошибка изменения статуса заказа.

**DEBUG**:
- подробная техническая диагностика.

В логи не записываем пароли, токены, персональные данные клиента, содержимое 3D-файлов, полный payload сообщений и параметры SQL-запросов с пользовательскими данными.

## 2. Мотивация

Сейчас команда восстанавливает проблему со слов клиента. Централизованные структурированные логи позволят быстро найти события конкретного заказа и понять, что произошло в конкретном сервисе.

Логирование должно снизить:

- среднее время поиска причины инцидента;
- среднее время обработки обращения поддержкой;
- количество инцидентов, для которых не удалось установить причину;
- количество повторных ошибок обработки сообщений;
- количество просроченных заказов из-за технических ошибок, которые долго оставались незамеченными.

Отдельную систему поиска аномалий на первом этапе не внедряем. Резкие изменения нагрузки отслеживаем по метрикам Prometheus, а по логам - всплески однотипных ошибок и некорректных событий.

### Приоритет внедрения логирования и трейсинга

1. **MES API + CRM API + RabbitMQ** - здесь меняются ключевые статусы и проходит интеграция, из-за которой заказ может не попасть в работу.
2. **Shop API** - точка входа B2C-заказов и загрузки 3D-моделей.
3. **PostgreSQL** - ошибки, блокировки и медленные запросы.
4. Остальные компоненты - после покрытия критического пути заказа.

## 3. Предлагаемое решение

### 3.1. Формат логов

Приложения пишут структурированные логи в формате JSON.

Основные поля:

- время;
- уровень;
- сервис;
- окружение;
- событие;
- `order_id`;
- `trace_id`;
- `span_id`;
- результат;
- код ошибки;
- длительность.

Названия бизнес-событий должны быть одинаковыми во всех сервисах, например:

- `order_created`;
- `order_status_changed`;
- `price_calculation_started`;
- `price_calculation_completed`;
- `message_published`;
- `message_consumed`.

### 3.2. Сбор и хранение

Используем OpenTelemetry Collector и OpenSearch для хранения логов

- приложения и инфраструктура формируют структурированные логи;
- OpenTelemetry Collector принимает их и передает в хранилище;
- OpenSearch хранит и индексирует логи;
- Grafana используется для поиска, фильтрации и анализа.

### 3.3. Связь логов с трейсингом

В прикладные логи добавляются `trace_id` и `span_id`.

По `order_id` можно найти историю заказа в логах, а по `trace_id` - найти связанный трейс в Jaeger.

### 3.4. Безопасность

- OpenSearch, OpenTelemetry Collector и Grafana доступны только из внутренней сети.
- Доступ сотрудников выполняется через корпоративную аутентификацию.
- Поддержке предоставляется доступ только на чтение.
- Доступ разработчиков ограничивается необходимыми окружениями.
- Передача логов выполняется по TLS.
- Секреты, токены, персональные данные, содержимое файлов и сообщений в логи не попадают.
- Ошибки перед записью проверяются на наличие чувствительных данных.

### 3.5. Хранение

Срок хранения:

- prod - 90 дней;
- dev и release - 14 дней.

## 4. Анализ логов и алертинг

Логи используются прежде всего для расследования конкретных проблем по `order_id` и `trace_id`.
Алерты по логам настраиваются только для событий, которые сложно или бессмысленно выражать обычной метрикой:
- повторяющиеся ошибки обработки заказа;
- невозможность изменить статус заказа;
- неуспешная обработка сообщения после всех повторных попыток;
- неизвестные или некорректные события.


Алерты по нагрузке, RPS, HTTP-ошибкам, состоянию RabbitMQ и инфраструктуре остаются в Prometheus.

## 5. Критерии выбора технологии хранения логов

Для централизованного хранения и анализа логов выбираем **OpenSearch**.
Основной сценарий "Александрита" — расследование проблемы конкретного заказа. Поддержке и разработчикам необходимо быстро восстановить последовательность событий и понять, в каком сервисе и по какой причине произошла ошибка.
Для этого система логирования должна позволять:
- искать по `order_id`, `trace_id`, `message_id`, сервису и уровню ошибки;
- объединять несколько условий в одном запросе;
- выполнять полнотекстовый поиск по сообщениям ошибок и исключениям;
- работать со структурированными логами в JSON;
- разделять данные разных сервисов и окружений;
- задавать срок хранения и автоматически очищать старые данные;
- связывать найденный лог с трассировкой в Jaeger через `trace_id`;
- масштабировать хранилище отдельно от приложений.

OpenSearch закрывает эти требования и подходит не только для хранения логов, но и для их последующего анализа. Это важно для текущей проблемы компании: вместо ручного просмотра файлов на отдельных инстансах сотрудник сможет найти все связанные события конкретного заказа одним запросом.

| Критерий | OpenSearch | Loki | ELK | Splunk |
|---|---|---|---|---|
| Поиск по полям и тексту | Сильный поиск и фильтрация | Поиск по меткам и содержимому | Сильный поиск и фильтрация | Сильный поиск и аналитика |
| Отдельные индексы по сервисам | Да | Используется другая модель хранения | Да | Да |
| Работа со структурированным JSON | Да | Да | Да | Да |
| Интеграция с Grafana | Да | Да | Да | Возможна |
| Интеграция с OpenTelemetry Collector | Да | Да | Да | Да |
| Управление сроком хранения | Да | Да | Да | Да |
| Ресурсоёмкость | Средняя/высокая из-за индексации | Обычно ниже | Средняя/высокая | Зависит от объёма и тарифа |
| Лицензирование | Открытая лицензия | Открытая лицензия | Зависит от используемой поставки | Проприетарная |
