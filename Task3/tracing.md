# Архитектурное решение по трейсингу

## 1. Что необходимо покрыть трейсингом

Трейсинг нужен для backend-компонентов, через которые проходит заказ:

- Shop API;
- CRM API;
- MES API;
- фоновые обработчики расчета стоимости;
- публикация и получение сообщений RabbitMQ;
- outbox-публикация;
- обращения к PostgreSQL и хранилищу 3D-файлов.

Основные места, где заказ может зависнуть или потерять ожидаемый переход:

- запрос между сервисами завершился ошибкой или слишком долго выполняется;
- данные сохранились в БД, но событие не было опубликовано;
- событие попало в RabbitMQ, но не было обработано consumer-ом;
- consumer получил событие, но завершился ошибкой до фиксации результата;
- расчет стоимости выполняется слишком долго;
- статус изменился в одной системе, но не дошел до другой;
- запрос к БД или хранилищу 3D-файлов выполняется слишком долго или завершается ошибкой.


## 2. Мотивация

Сейчас по жалобе клиента сложно определить, на каком шаге остановился конкретный заказ.

Трейсинг позволит:

- найти операции конкретного заказа по `order.id`;
- увидеть последний успешно выполненный шаг;
- определить сервис или интеграцию, где возникла задержка или ошибка;
- связать HTTP-запросы, сообщения RabbitMQ и обращения к БД;
- быстрее разбирать жалобы B2C-клиентов и B2B-партнеров.

Таким образом снизится:
- Среднее время поиска причины инцидента
- Время разбора обращения клиента
- Количество заказов с неизвестной причиной зависания
- Доля просроченных заказов


Трейсинг сам по себе не гарантирует доставку сообщений и не является источником истины по статусу заказа.

## 3. Предлагаемое решение

### 3.1. Инструментирование приложений

Для распределенного трейсинга используем **OpenTelemetry**.

Подключаем:

- OpenTelemetry для Java и .Net
- автоматическое создание спанов для HTTP и запросов к БД;
- ручные бизнес-спаны для ключевых операций заказа.

Примеры бизнес-операций:

- `order.submit`;
- `order.price.calculate`;
- `order.status.change`;
- `rabbitmq.publish`;
- `rabbitmq.consume`.

### 3.2. Передача контекста между сервисами

Для HTTP используется стандартный заголовок `traceparent`.

При публикации сообщения в RabbitMQ `traceparent` записывается в headers сообщения. Consumer извлекает его и продолжает связанную трассировку.

Дополнительно в спаны передается `order.id`, чтобы можно было найти все технические операции конкретного заказа.

### 3.3. Сбор и хранение трейсов

Приложения отправляют трейсы по протоколу OTLP в **OpenTelemetry Collector**.

OpenTelemetry Collector - это не Prometheus и не компонент, который опрашивает `/metrics`.
- метрики Prometheus забирает сам по pull-модели;
- трейсы приложения отправляют в OpenTelemetry Collector по push-модели.

Его задача в данном решении:

- принимать трейсы от приложений;
- выполнять пакетную отправку;
- фильтровать ненужные или чувствительные атрибуты;
- выполнять повторные попытки отправки;
- централизованно отправлять трейсы в хранилище.

Для хранения и просмотра трейсов используем **Jaeger**. Через его UI команда сможет искать трассировки по `trace_id`, сервису, ошибкам и атрибутам заказа.

### 3.4. Сэмплирование и срок хранения

Сэмплируются именно **трейсы**, а не сами метрики

Полностью сохраняем:

- создание заказа;
- изменение статуса;
- расчет стоимости;
- публикацию и обработку событий RabbitMQ;
- ошибки.

Для второстепенных read-only запросов можно сохранять только часть трейсов.

Это уменьшает объем хранилища, но не должно приводить к потере истории прохождения заказа.

Стартовый срок хранения подробных трейсов - **30 дней**. После накопления статистики срок можно увеличить, или складывать в холодное хранилище.

## 4. Компромиссы

- Трейсинг создает дополнительную нагрузку на API и workers: создание спанов, распространение контекста и экспорт телеметрии используют CPU, память и сеть.
- Появляется дополнительная инфраструктура - OpenTelemetry Collector и Jaeger. Для них нужны ресурсы, обновления, резервирование и мониторинг.
- Хранение 100% трейсов при росте нагрузки может потребовать значительного объема диска. Поэтому второстепенные запросы можно сэмплировать.
- Слишком агрессивное сэмплирование может удалить нужный trace. Критические операции заказа и ошибки поэтому сохраняются полностью.
- При падении приложения до экспорта телеметрии часть трейса может отсутствовать. Отсутствие спана не является доказательством потери заказа.
- При недоступности OpenTelemetry Collector возможна потеря части телеметрии после исчерпания локальных буферов.
- Один trace неудобно держать открытым несколько недель. Поэтому долгоживущий процесс заказа связывается через `order.id`, а не через один непрерывный trace.
- Трейсинг не восстановит историю заказов, обработанных до его внедрения.
- Если внешняя система не передает trace context, полный путь за пределами системы «Александрита» увидеть нельзя.
- Трейсинг не заменяет Transactional Outbox и идемпотентность: он помогает обнаружить проблему, но сам не гарантирует доставку события.
- Трейсинг не является источником истины по текущему статусу заказа. Актуальный статус хранится в БД владельца данных.
- Объем накладных расходов и необходимый процент сэмплирования нужно подтвердить нагрузочным тестированием на release-окружении.

## 5. Безопасность

- OpenTelemetry Collector и Jaeger размещаются во внутренней сети и не публикуются напрямую в интернет.
- Доступ к Jaeger предоставляется только сотрудникам компании через корпоративную аутентификацию.
- Поддержке достаточно read-only доступа; административные права выдаются только ответственным инженерам.
- Передача телеметрии между приложениями, Collector и Jaeger выполняется по TLS.
- Сетевые правила разрешают отправку телеметрии в Collector только доверенным сервисам.
- Секреты и учетные данные хранятся вне исходного кода.
- В спаны запрещено записывать персональные данные, токены, содержимое сообщений и 3D-файлов.
- Доступ к системе трейсинга и административные действия журналируются.
- Для трейсов задается ограниченный срок хранения.
