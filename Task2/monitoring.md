# Выбор и настройка мониторинга в системе

## 1. Мотивация

Сейчас Яндекс Метрика показывает только поведение пользователей сайта и не покрывает заказы, которые приходят через внешний API, работу CRM, MES, RabbitMQ, баз данных и 3D-хранилища.

Мониторинг нужен, чтобы:
- видеть полный поток заказов из B2C и B2B-каналов;
- находить место, где заказ задержался: API, очередь, расчет стоимости, CRM, MES или БД;
- выявлять деградацию раньше, чем поступят жалобы клиентов;
- понять причину медленной загрузки первой страницы MES;
- планировать масштабирование на основе фактической нагрузки;
- быстрее разбирать инциденты и снижать риск потери контрактов.

Для бизнеса это дает измеримый результат: меньше просроченных заказов, меньше времени на поиск причин сбоев, более предсказуемая работа системы при росте нагрузки.

## 2. Выбор подхода к мониторингу

Для Shop API, CRM API и MES API используется подход «Четыре золотых сигнала»:

- Latency - время ответа;
- Traffic - количество запросов;
- Errors - количество и доля ошибок;
- Saturation - степень насыщения системы.

Этот подход выбран потому, что в системе уже есть признаки деградации под растущей нагрузкой: MES медленно открывает список заказов, число заказов постоянно растет, а каждый сервис работает только в одном экземпляре. Поэтому важно отслеживать не только запросы, ошибки и задержки, но и момент, когда сервис или связанный с ним ресурс приближается к пределу.

Для инфраструктуры используется USE:

- Utilization - загрузка ресурса;
- Saturation - приближение к пределу ресурса;
- Errors - ошибки ресурса.

USE применяется для облачных инстансов (сервисы, PostgreSQL и RabbitMQ). Метрики этих ресурсов одновременно используются как показатели насыщенности для API.

Дополнительно нужны бизнес-метрики по жизненному циклу заказа. Они покажут не только техническое состояние сервисов, но и влияние проблем на клиентов.

### 3. Метрики

#### 3.1. Shop API, CRM API, MES API

Метрики этого раздела соответствуют четырем золотым сигналам.

#### Traffic

1) RPS для каждого API

Зачем:
- видеть рост нагрузки;
- сравнивать нагрузку между сервисами;
- связывать рост запросов с ростом задержек и ошибок.

Лейблы:
- service: shop-api / crm-api / mes-api;
- endpoint;
- method;
- source: web / api, где применимо.


2) RPS на клиента для внешнего MES API

Зачем:
- понимать, какой B2B-клиент создает основную нагрузку;
- выявлять аномальные всплески;
- при необходимости вводить rate limit.

Лейблы:
- partner_id;
- endpoint.

Для Shop API и CRM API метрику по каждому пользователю не собираем, чтобы не создавать метрики с высокой кардинальностью.

#### Latency


3) Response time (latency) для Shop API, CRM API, MES API
Зачем:
- контролировать скорость работы API;
- отдельно видеть деградацию MES-эндпоинтов, которые используются на первой странице MES.

Отслеживать p50, p95, p99.

Лейблы:
- service;
- endpoint;
- method;
- status_code.

#### Errors

4) HTTP 2xx и HTTP 5xx для каждого API

Зачем:
- считать долю успешных и ошибочных запросов;
- быстро обнаруживать технические сбои.

Лейблы:
- service;
- endpoint;
- method;
- status_code.

#### Saturation

5) CPU Utilisation для Shop API, CRM API, MES API

Зачем:
- понимать, хватает ли вычислительных ресурсов;
- выявлять насыщение единственного инстанса приложения.

Лейблы:
- service;
- instance;
- environment.

6) Memory Utilisation для Shop API, CRM API, MES API

Зачем:
- выявлять нехватку памяти, утечки и риск OOM;
- понимать необходимость увеличения ресурсов или числа инстансов.

Лейблы:
- service;
- instance;
- environment.

Также к показателям насыщенности API относятся:
- количество подключений к соответствующей БД;
- CPU и memory БД;
- количество сообщений в RabbitMQ для интеграций CRM и MES;
- количество сообщений in flight.

Эти показатели собираются на уровне инфраструктуры и отображаются рядом с метриками API на дашбордах.

#### 3.2. RabbitMQ

1) Количество dlq сообщений

Зачем:
- видеть сообщения, которые не были обработаны;
- такие сообщения могут означать потерянный или зависший переход заказа между CRM и MES.

Лейблы:
- queue;
- exchange;
- routing_key;
- consumer_service.

2) Количество in-flight сообщений

Зачем:
- видеть количество сообщений, которые уже забраны consumer-ами, но еще не подтверждены;
- рост показателя может означать зависание обработчиков.

Лейблы:
- queue;
- consumer_service.

3) Количество сообщений в очереди

Зачем:
- видеть накопление необработанных сообщений.

Лейблы:
- queue.

4) Дополнительная метрика: возраст самого старого сообщения в очереди

Зачем:
- количество сообщений само по себе не показывает, сколько времени заказ ждет обработки;
- возраст сообщения напрямую показывает задержку.

Лейблы:
- queue.

#### 3.3. PostgreSQL

Для Shop DB и MES DB:

1) Memory Utilisation
Зачем:
- контролировать использование памяти БД;
- выявлять деградацию из-за нехватки ресурсов.

Лейблы:
- database;
- instance;
- environment.

2) Количество подключений
Зачем:
- контролировать пул подключений;
- не допускать исчерпания лимита соединений.

Лейблы:
- database;
- instance.

3) Заполненность базы
Зачем:
- планировать увеличение диска;
- не допускать остановки БД из-за нехватки места.

Лейблы:
- database;
- instance.

4) CPU Utilisation БД
Зачем:
- понимать, связана ли медленная работа API и MES-дашборда с нагрузкой на БД.

Лейблы:
- database;
- instance.

5) Время выполнения запросов
Зачем:
- найти тяжелые запросы, особенно запрос списка заказов по статусам в MES;
- проверить, помогают ли индексы, фильтры и пагинация.

Лейблы:
- database;
- query_name.

#### 3.4. Хранилище 3D-файлов

1) Размер хранилища S3
Зачем:
- контролировать рост объема моделей;
- планировать стоимость и лимиты хранения.

Лейблы:
- bucket;
- environment.

2) Ошибки загрузки/чтения и latency операций
Зачем:
- загрузка 3D-файла участвует в оформлении заказа;
- проблемы с хранилищем могут блокировать дальнейшую обработку.

Лейблы:
- тип операции: upload / download;
- ответ: success / error.

#### 3.5. Бизнес-метрики заказа

Эти метрики критичны для текущей проблемы и должны собираться отдельно от технических.

1) Количество заказов в каждом статусе
Зачем:
- видеть, на каком этапе накапливаются заказы.

Лейблы:
- status;
- source: web / api.

2) Время нахождения заказа в текущем статусе
Зачем:
- находить зависшие заказы.

Отслеживать p50, p95, p99.

Лейблы:
- status;
- source.


3) Полное время выполнения заказа: SUBMITTED -> CLOSED
Зачем:
- измерять фактический срок выполнения заказа.

Лейблы:
- source.

4) Время расчета стоимости в MES
Зачем:
- расчет занимает от нескольких минут до 30 минут и может стать узким местом при росте числа заказов.

Отслеживать p50, p95, p99.

Лейблы:
- source;
- success / error.

В метрики не добавлять `order_id` и обычный `user_id`: это создаст слишком большое число временных рядов. Для поиска конкретного заказа использовать логи.

### 4. План действий

1) Развернуть центральное хранилище метрик на базе Prometheus.
2) Развернуть Grafana для дашбордов.
3) Подключить сбор метрик из приложений и предоставить /metrics ручку, Prometheus периодически опрашивает ее.
4) Подключить инфраструктурные экспортеры метрик. Чтобы Postgres и RabbitMQ также отправляли метрики в ручке `/metrics`
5) Добавить бизнес-метрики жизненного цикла заказа в Shop API, CRM API и MES API.
6) Добавить метрики длительности расчета стоимости и обработки сообщений RabbitMQ.
7) Создать дашборды:
   - состояние API;
   - RabbitMQ;
   - PostgreSQL;
   - MES dashboard;
   - поток заказов и просроченные заказы.
8) Настроить алертинг и уведомления в разные каналы (мессенджер, звонки и тд). Сконфигурировать пороги для срабатывания алертов
9) Хранить конфигурацию мониторинга и алертов в репозитории и изменять через CI/CD.

### 5. Показатели насыщенности и реакция

Базовые пороги на старте:

- CPU приложения > 80% в течение 10 минут.
    * Причина: остается небольшой запас для всплесков.
    * Действие: warning в канал команды. При > 90% в течение 5-10 минут - критичный алерт, звонок дежурному и масштабирование/увеличение ресурсов.

- Memory приложения > 85% в течение 10 минут.
  * Причина: высокий риск OOM и деградации.
  * Действие: warning. При > 90% - критичный алерт, звонок дежурному и проверка утечек памяти/увеличение ресурсов.

- PostgreSQL connections > 80% от максимума в течение 5 минут.
  * Причина: дальнейший рост может привести к отказам новых подключений.
  * Действие: проверить connection pool и долгие запросы. При > 90% - критичный алерт и звонок.

- Диск/размер БД > 80% доступного объема.
  * Причина: нужен запас на рост заказов и служебные операции БД.
  * Действие: тикет на расширение. При > 90% - критичный алерт со звонком дежурному и срочное увеличение объема.

- RabbitMQ: очередь ready стабильно растет 10 минут или возраст старого ready-сообщения > 5 минут.
  * Причина: consumer-ы не успевают обрабатывать входящий поток.
  * Действие: алерт, проверка CRM/MES consumer-ов. При длительном росте - увеличить число consumer-ов/инстансов.

- Dead-letter queue > 0.
  * Причина: сообщение уже не прошло штатную обработку и потенциально связано с потерянным заказом.
  * Действие: сразу создать и тикет на разбор сообщения.

Пороговые значения являются стартовыми. После накопления статистики за несколько недель их нужно скорректировать, чтобы алерты отражали реальные проблемы, а не обычные пики нагрузки.
